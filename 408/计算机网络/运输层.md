## 4.1 运输层概述与服务模型

### 4.1.1 运输层的功能与作用

运输层在整个网络协议栈中扮演着至关重要的角色。从逻辑上看，它位于应用层之下，网络层之上。其主要功能包括：复用（Multiplexing）和分用（Demultiplexing）。
- 复用指的是在发送端，多个应用进程可以同时使用一个运输层协议（如 TCP 或 UDP），并通过端口号来区分不同的应用进程，最终将它们的数据封装成段（Segment）后，统一交给网络层处理。
- 分用则是在接收端，运输层从网络层接收到数据报后，根据其中的端口号将数据报正确地交付给目标应用进程。这种机制使得单个主机能够同时运行多个网络应用，极大地提升了网络资源的利用效率。

运输层提供的服务可以分为两大类：面向连接的服务和无连接的服务。
- 面向连接的服务，以 TCP（传输控制协议）为代表，它在数据传输前会建立一条逻辑上的连接，在连接期间保证数据的可靠传输、有序交付和流量控制等功能。这种服务模式虽然开销较大，但适用于对数据完整性和顺序要求高的应用，如文件传输、电子邮件等。
- 无连接的服务，以 UDP（用户数据报协议）为代表，它在数据传输前不建立连接，直接将应用层数据封装成数据报发送。这种模式开销小、传输速度快，但不能保证数据的可靠性，适用于对实时性要求高但允许少量数据丢失的应用，如实时视频、语音通话、DNS 查询等。运输层是整个网络体系中实现端到端通信的关键，它确保了数据能够准确、有效地从一个主机的特定进程传送到另一个主机的特定进程。

### 4.1.2 运输层与网络层的区别与联系

虽然运输层和网络层都涉及到数据的传输，但它们的职责范围有着本质的区别。网络层，以 IP 协议为核心，提供的是主机到主机的尽力而为（Best-effort）数据报传输服务。它主要关注如何将数据报从源主机路由到目的主机，但不关心数据报是否完整、是否有序到达，也不提供任何错误恢复或重传机制。网络层是“点到点”的通信，即主机之间的通信。

而运输层则是在网络层提供的服务基础上，进一步为应用进程提供==端到端==的逻辑通信。它将网络层提供的不可靠、尽力而为的服务，通过诸如可靠传输、流量控制、拥塞控制等机制，转换成应用层所需要的可靠或不可靠服务。运输层是“端到端”的通信，即进程之间的通信。我们可以形象地将网络层比作是邮政系统，负责将信件从一个城市送到另一个城市；而运输层则像是邮政系统内部的特定服务，确保信件能准确无误地送到特定收件人（应用进程）手中。运输层的这种“端到端”逻辑通信，正是它与网络层“主机到主机”通信的根本区别。

### 4.1.3 运输层的协议端口号与套接字

在多任务操作系统中，一个主机上可能会同时运行多个网络应用，例如浏览器、邮件客户端、FTP 服务等。为了将运输层收到的数据正确地交付给特定的应用进程，运输层引入了协议端口号（Protocol Port Number）的概念。端口号是一个 16 位的正整数，用于标识主机上的一个应用进程。它将运输层报文段中的数据交付给正确的目标应用进程。

套接字（Socket）是网络编程中的一个重要概念，它是应用层与运输层之间的接口。套接字由 IP 地址和端口号组成，可以唯一地标识网络上的一个通信端点。在一个 TCP 连接中，通信双方的套接字是唯一的，由一个四元组来唯一标识：(源IP地址, 源端口号, 目的IP地址, 目的端口号)。这个四元组在整个连接的生命周期内是固定的，确保了数据能够准确无误地在通信双方的特定进程之间传输。对于 UDP 协议而言，一个 UDP 套接字则由 (IP地址, 端口号) 组成。套接字的概念为程序员提供了一种抽象机制，使得他们可以方便地进行网络通信编程，而无需直接处理底层复杂的协议细节。

## 4.2 UDP 协议：简单、高效的无连接服务

### 4.2.1 UDP 协议概述与特点

UDP（User Datagram Protocol，用户数据报协议）是一种无连接的、不可靠的运输层协议。它的设计哲学是简单、高效、低开销。UDP 在发送数据之前，无需进行三次握手建立连接，直接将数据封装成 UDP 用户数据报，然后交给网络层发送。由于不维护连接状态，每个 UDP 数据报都是独立发送的，因此接收方可能会收到乱序、重复甚至丢失的数据报。UDP 的主要特点可以归纳为以下几点：

- 无连接性：发送数据前无需建立连接，减少了连接建立和释放的开销。
- 尽力而为：不保证可靠传输，不提供数据重传、流量控制或拥塞控制。
- 报文边界：UDP 对应用层交下来的报文，在添加首部后就一次性交付给 IP 层，发送方对应用层数据报的长度限制是基于 IP 层数据报长度的，即 65507 字节（65535 - 8 - 20）。
- 首部开销小：UDP 首部只有 8 个字节，比 TCP 的 20 字节首部要小得多，这使得其在传输效率上具有优势。
- 一对一、一对多、多对一、多对多通信：UDP 不限制通信模式，支持单播、多播和广播。

UDP 的这种特性使其特别适用于那些对实时性要求高、但对少量数据丢失不敏感的应用，如 DNS（域名系统）、VoIP（网络电话）、在线游戏、流媒体等。在这些应用中，即使偶尔丢失一两个数据包，用户体验也不会受到太大影响，而如果为了可靠性进行重传，反而会增加延迟，影响实时效果。

### 4.2.2 UDP 用户数据报格式与字段解析

UDP 的用户数据报由一个固定的 8 字节首部和可变长度的数据部分组成。UDP 首部非常简洁，包含四个字段，每个字段都是 16 位（2 字节），共 8 个字节。

| 字段名称   | 字段长度 | 字段含义                                                     |
|------------|----------|------------------------------------------------------------|
| 源端口     | 16 位   | 源主机上发送进程的端口号。如果不需要，可以置为 0，但一般都会填充。 |
| 目的端口   | 16 位   | 目的主机上接收进程的端口号。这是分用时最重要的信息。       |
| 长度       | 16 位   | UDP 用户数据报的长度，单位是字节。该长度包括首部和数据部分。 |
| 校验和     | 16 位   | UDP 用户数据报的首部和数据部分的校验和。用于检验数据是否在传输过程中出错。 |

源端口（Source Port）和目的端口（Destination Port）字段用于标识发送和接收数据的应用进程，实现运输层的复用和分用功能。长度（Length）字段指明了整个 UDP 用户数据报的长度，包括 8 字节的首部和数据部分。这个字段的存在使得接收方可以根据长度信息准确地将数据报从 IP 数据报中提取出来。校验和（Checksum）字段是 UDP 协议中唯一提供差错检测的机制。它采用的是反码算术运算，计算覆盖了 UDP 首部和数据部分的伪首部。这个==伪首部是 UDP 校验和计算时增加的，它包含源 IP 地址、目的 IP 地址、协议号和 UDP 长度==等信息，从而增强了校验和的可靠性。如果校验和字段为 0，则表示不使用校验和功能（但在 IPv4 中很少见，IPv6 中要求必须使用）。当接收方收到数据报后，会重新计算校验和并与接收到的校验和字段进行比对。如果一致，则认为数据报无差错；如果不一致，接收方通常会简单地丢弃这个数据报，而不会进行任何错误恢复。

### 4.2.3 UDP 在实际应用中的案例分析

UDP 协议的简单性和高效性，使其在许多特定应用场景中表现出色。

- **域名系统（DNS）**：当用户在浏览器中输入一个网址时，客户端需要向 DNS 服务器查询对应的 IP 地址。这个查询过程通常使用 UDP。因为 DNS 查询是一个简单的请求-响应模式，数据量小，并且对实时性有较高要求。如果查询失败，客户端可以简单地重发请求，而无需复杂的连接建立过程。UDP 的低延迟特性使得 DNS 查询能够快速完成，提升了用户体验。
  
- **流媒体与实时多媒体应用（VoIP、视频会议）**：对于在线视频播放、网络电话（如 Skype、Zoom）等应用，实时性是其核心要求。即使丢失一两个视频帧或语音数据包，用户通常也只会感受到轻微的卡顿或音质下降，但为了重传这些数据而导致的延迟，则会严重影响通信的连贯性和流畅度。UDP 的无连接、无重传特性正好满足了这种需求，它允许数据快速传输，即使有少量丢失。
  
- **在线游戏**：许多在线多人游戏（尤其是第一人称射击游戏）也大量使用 UDP。游戏服务器需要以极高的频率向所有玩家发送位置、状态等数据更新。如果使用 TCP，重传机制会引入额外的延迟，导致“网络卡顿”的感觉。而 UDP 允许服务器快速发送数据，即使有少量数据包丢失，游戏客户端也可以通过后续更新来弥补，从而保证了游戏的流畅性。
  
- **SNMP（简单网络管理协议）**：SNMP 用于网络设备的管理和监控。管理站向设备发送请求或设备向管理站发送告警信息，这些通信通常是短暂的，并且允许少量信息丢失。UDP 简单、低开销的特点非常适合这种轻量级的通信模式。

在这些应用中，UDP 的优势在于其极低的协议开销和传输延迟。但需要注意的是，如果应用需要可靠性，通常会在应用层自行实现一些可靠性机制，例如对数据包进行编号、确认和重传，来弥补 UDP 在这方面的不足。

## 4.3 TCP 协议：可靠、面向连接的服务

### 4.3.1 TCP 协议概述与特点

TCP（Transmission Control Protocol，传输控制协议）是一种面向连接的、可靠的、基于字节流的运输层协议。与 UDP 形成鲜明对比，TCP 协议为上层应用提供了高度可靠的数据传输服务。在进行数据传输之前，通信双方必须先建立一条逻辑上的连接，这个过程称为“三次握手”。在数据传输过程中，TCP 提供了诸多机制来保证数据的可靠性，包括序号、确认应答、超时重传、流量控制和拥塞控制等。当数据传输完毕后，通信双方还会通过“四次挥手”来释放连接。

TCP 的核心特点可以概括为：

- 面向连接：在数据传输前必须建立连接，传输完成后必须释放连接。
- 可靠传输：通过序号、确认应答和超时重传等机制确保数据不丢失、不重复、不乱序。
- 面向字节流：TCP 将应用层数据视为一个无结构的字节流，将数据进行分段并编号，最终以字节为单位进行传输和交付。
- 全双工通信：TCP 连接允许数据在两个方向上同时传输。
- 流量控制：通过滑动窗口机制，协调通信双方的发送速率和接收速率，防止发送方发送速度过快，导致接收方缓冲区溢出。
- 拥塞控制：通过多种算法，动态调整发送速率，防止因网络拥塞而导致性能下降甚至崩溃。

TCP 协议的这些强大功能使其成为互联网上最主流的运输层协议，广泛应用于 HTTP/HTTPS、FTP、SMTP（电子邮件）、SSH 等对数据完整性和可靠性要求极高的应用。

### 4.3.2 TCP 报文段格式与字段详解

TCP 报文段是 TCP 传输的基本单位，其首部是协议复杂性的体现。TCP 首部最小长度为 20 字节，最大为 60 字节，其格式如下：

| 字段名称            | 字段长度 | 字段含义                                                   |
|---------------------|----------|----------------------------------------------------------|
| 源端口              | 16 位   | 源主机上发送进程的端口号。                               |
| 目的端口            | 16 位   | 目的主机上接收进程的端口号。                             |
| 序号（Sequence Number） | 32 位   | 本报文段第一个数据字节的序号。在连接建立时，双方随机选择一个初始序号。 |
| 确认号（Acknowledgment Number） | 32 位   | 期望收到对方下一个报文段的第一个数据字节的序号。它表示对已收到数据包的确认。 |
| 数据偏移            | 4 位    | 占 4 位，表示 TCP 首部长度。单位是 4 字节（32 位字）。   |
| 保留                | 6 位    | 保留字段，目前都置为 0。                                 |
| 标志位（Flags）     | 6 位    | 包括 URG, ACK, PSH, RST, SYN, FIN 六个标志位。           |
| 窗口（Window）      | 16 位   | 接收方告诉发送方自己还有多少缓冲区可以接收数据，用于流量控制。 |
| 校验和（Checksum）  | 16 位   | 对整个 TCP 报文段（首部和数据）进行校验。               |
| 紧急指针（Urgent Pointer） | 16 位   | 只有在 URG 标志位为 1 时才有效，它是一个偏移量，指向报文段中紧急数据的最后一个字节。 |
| 选项（Options）     | 变长    | 最多 40 字节，用于协商 MSS（最大报文段长度）、选择确认 SACK 等。 |
| 填充                | 变长    | 用于使整个首部长度为 32 位的倍数。                       |
| 数据部分            | 变长    | 实际传输的应用层数据。                                   |

序号（Sequence Number）：这是 TCP 实现可靠传输和有序交付的关键。它不是报文段的序号，而是报文段中数据部分的第一个字节的序号。在连接建立时，通信双方会协商一个初始序号（Initial Sequence Number, ISN）。

确认号（Acknowledgment Number）：确认号是发送方期望收到的对方下一个报文段的数据的第一个字节的序号。例如，如果收到了序号为 1000、长度为 100 字节的数据，那么确认号就会是 1000 + 100 = 1100。它表示发送方已经成功收到了 1099 字节之前的所有数据。

数据偏移（Header Length）：由于选项字段的存在，TCP 首部长度是可变的，这个字段用于指示 TCP 首部长度，以便接收方能够正确地解析数据部分。它的单位是 4 字节，所以 4 位字段最大能表示 $2^4 - 1 = 15$。$15 \times 4 = 60$ 字节，即 TCP 首部的最大长度。

标志位（Flags）：
- URG：紧急（Urgent），当它为 1 时，表示报文段中有紧急数据，紧急指针字段有效。
- ACK：确认（Acknowledgment），当它为 1 时，表示确认号字段有效。TCP 规定，在连接建立后所有传送的报文段都必须把 ACK 置为 1。
- PSH：推送（Push），当它为 1 时，表示接收方应尽快将数据交付给应用层，而不是等待缓冲区满。
- RST：复位（Reset），当它为 1 时，表示连接出现严重错误，必须立即释放连接，并重新建立。
- SYN：同步（Synchronize），用于在连接建立时同步序号。当 SYN=1, ACK=0 时，表示这是一个连接请求报文段；当 SYN=1, ACK=1 时，表示这是一个连接请求的确认报文段。
- FIN：终止（Finish），用于释放连接。当 FIN=1 时，表示发送方的数据已发送完毕，请求释放连接。

窗口（Window）：用于流量控制。这个字段由==接收方填充==，告诉发送方自己当前还可以接收多少字节的数据。发送方会根据这个值来调整自己的发送速率，避免因发送过快导致接收方缓冲区溢出。

校验和（Checksum）：与 UDP 协议类似，TCP 校验和也用于检测报文段的首部和数据部分在传输过程中是否出错。它同样也包含一个伪首部。

### 4.3.3 TCP 连接管理：三次握手与四次挥手

TCP 是面向连接的协议，其连接的建立和释放是其核心机制之一。

#### 三次握手（Three-way Handshake）：建立连接

三次握手是 TCP 建立连接的过程，目的是为了同步双方的序列号，并告知对方自己的 MSS（最大报文段长度）。

1. **第一次握手**：客户端发送一个 SYN 报文段到服务器，并选择一个初始序号 ISN_c。报文段中的标志位 SYN=1，序号字段 Seq = ISN_c。客户端进入 SYN_SENT 状态。
2. **第二次握手**：服务器收到 SYN 报文段后，如果同意建立连接，会向客户端发送一个 SYN+ACK 报文段。这个报文段中的标志位 SYN=1, ACK=1，确认号字段 Ack = ISN_c + 1，同时服务器也选择一个自己的初始序号 ISN_s，并将其放入序号字段 Seq = ISN_s。服务器进入 SYN_RECEIVED 状态。
3. **第三次握手**：客户端收到服务器的 SYN+ACK 报文段后，会向服务器发送一个 ACK 报文段。标志位 ACK=1，序号字段 Seq = ISN_c + 1，确认号字段 Ack = ISN_s + 1。客户端进入 ESTABLISHED 状态。当服务器收到这个 ACK 报文段后，也进入 ESTABLISHED 状态。

至此，TCP 连接建立成功，双方可以开始全双工数据传输。三次握手确保了双方都能够确认对方的接收和发送能力正常，并同步了彼此的初始序列号。

#### 四次挥手（Four-way Handshake）：释放连接

四次挥手是 TCP 释放连接的过程，由于 TCP 是全双工的，因此每个方向上的数据流都需要独立地终止。

1. **第一次挥手**：客户端发送一个 FIN 报文段，标志位 FIN=1，表示它已没有数据要发送，请求关闭连接。客户端进入 FIN_WAIT_1 状态。
2. **第二次挥手**：服务器收到 FIN 报文段后，向客户端发送一个 ACK 报文段，确认客户端的 FIN 请求。服务器进入 CLOSE_WAIT 状态。此时，TCP 连接处于半关闭状态，客户端已经没有数据要发送，但服务器如果还有数据要发送，则可以继续发送。
3. **第三次挥手**：服务器在完成所有数据发送后，也发送一个 FIN 报文段，标志位 FIN=1，表示它也准备关闭连接。服务器进入 LAST_ACK 状态。
4. **第四次挥手**：客户端收到服务器的 FIN 报文段后，向服务器发送一个 ACK 报文段，确认服务器的 FIN 请求。客户端进入 TIME_WAIT 状态，并等待 2MSL（最长报文段生命周期）的时间，确保服务器能够收到 ACK 报文段。服务器收到 ACK 报文段后，直接进入 CLOSED 状态。当客户端的 TIME_WAIT 时间结束后，也进入 CLOSED 状态，至此连接完全释放。

四次挥手之所以是四次，是因为服务器在收到 FIN 请求后，可能还有数据需要发送，它不能立即关闭连接。因此，服务器的 ACK 和 FIN 报文段是分开发送的，从而导致了四次挥手。

## 4.4 可靠传输机制与设计思想

### 4.4.1 可靠传输的基本原理与实现

可靠传输是指发送方发送的任何数据，最终都能无差错、不重复、不丢失、按序地到达接收方。TCP 协议通过一系列精妙的机制，将下层网络层提供的不可靠、尽力而为的服务，转换为上层应用所需的可靠服务。这些机制主要包括：校验和、序号、确认应答和超时重传。

- **校验和（Checksum）**：TCP 校验和能够检测出报文段在传输过程中是否出现了位错误。如果接收方发现校验和不正确，会丢弃该报文段，并不会发送确认，从而依赖超时重传机制来解决。
- **序号（Sequence Number）**：每个 TCP 报文段都带有一个序号，标识报文段中第一个数据字节在整个数据流中的位置。通过序号，接收方可以对乱序到达的报文段进行重新排序，并识别和丢弃重复的报文段。
- **确认应答（Acknowledgment）**：接收方在成功收到报文段后，会发送一个确认报文段给发送方，其中的确认号字段表明了它期望收到的下一个报文段的序号。TCP 采用的是累计确认的方式，即确认号 Ack = N 表示发送方已经成功收到了序号小于 N 的所有数据。
- **超时重传（Timeout and Retransmission）**：这是 TCP 确保可靠传输的核心机制。发送方在发送一个报文段后，会启动一个定时器。如果在定时器到期之前没有收到该报文段的确认，则认为该报文段已丢失，会重新发送该报文段。超时重传时间（RTO）的设置是至关重要的，RTO 过短会导致不必要的重传，增加网络负担；RTO 过长则会降低传输效率。TCP 协议采用了一种自适应的算法来动态调整 RTO，根据历史往返时间（RTT）的测量值，平滑地计算出一个合理的 RTO 值。

### 4.4.2 停止-等待协议与滑动窗口机制

为了更好地理解 TCP 的可靠传输，我们可以先从最简单的停止-等待（Stop-and-Wait）协议入手。这是一个最基础的可靠传输协议，其工作流程是：发送方发送一个分组后，必须等待接收方的确认分组才能发送下一个分组。这种方式的优点是简单可靠，但缺点是效率极低，因为在等待确认的期间，发送方不能发送任何新的数据，信道利用率非常低。

为了解决停止-等待协议效率低下的问题，TCP 引入了滑动窗口（Sliding Window）机制。滑动窗口协议允许发送方在未收到确认之前，连续发送多个分组。窗口的大小决定了发送方可以发送但尚未得到确认的分组数量。

滑动窗口的核心思想是维护一个逻辑上的窗口，窗口内的报文段可以被发送。窗口的大小是动态变化的，它受到接收方缓存大小和网络拥塞状况的影响。发送方和接收方各维护一个发送窗口和接收窗口。

- **发送窗口**：发送方维护的窗口，包含了已发送但尚未收到确认的报文段，以及可以立即发送的报文段。发送窗口的左边界是已发送并已确认的报文段的下一个字节序号，右边界是发送方可以发送的最后一个字节的序号。
- **接收窗口**：接收方维护的窗口，它的大小由接收方决定，并通过 TCP 报文段的窗口字段告知发送方。接收窗口的左边界是期望收到的下一个报文段的序号，右边界是接收方能接收的最后一个字节的序号。

当发送方收到一个确认报文段时，发送窗口的左边界会向右移动，表示该报文段已被确认。当接收方将数据交付给应用层后，接收窗口的左边界也会向右移动，表示可以接收更多的数据，并通过确认报文段将新的窗口大小告知发送方。这种机制在确保可靠性的同时，大大提高了数据传输的吞吐量，实现了流量控制。

### 4.4.3 TCP 的超时重传与选择重传

当发送方在规定时间内没有收到确认报文时，就会触发超时重传。TCP 的超时重传机制是其可靠性的重要基石。

超时重传时间（RTO）的计算非常关键。如果 RTO 太短，可能会在网络延迟较高时导致不必要的重传；如果 RTO 太长，则会导致网络效率低下。TCP 使用一种动态算法来计算 RTO，主要基于平滑往返时间（SRTT)，和RTT偏差的加权平均值（RTTVAR）

  * 新的SRTT = $(1 - \alpha) \cdot \text{旧的SRTT} + \alpha \cdot \text{新的RTT样本}$ （$\alpha$ 通常为1/8）
  * $RTTVAR = (1 - \beta) \cdot \text{旧的RTTVAR} + \beta \cdot |\text{SRTT} - \text{新的RTT样本}|$ （$\beta$ 通常为1/4）
  * RTO的计算公式：$RTO = \text{SRTT} + 4 \cdot \text{RTTVAR}$
* RTO的优化机制：
  * 指数退避（Exponential Backoff）：如果一个报文段连续多次重传失败，RTO会翻倍。这是一种应对网络拥塞的策略，通过减缓发送速率来给网络恢复时间。
  * Karn算法：为避免重传报文的RTT测量产生歧义，该算法规定不使用重传报文的RTT来更新SRTT和RTTVAR。

选择重传（Selective Repeat）是另一种提高可靠传输效率的机制，它弥补了累计确认的不足。在 TCP 传统的累计确认中，如果发送方发送了多个报文段，但中间的一个报文段丢失了，即使接收方收到了后续的报文段，也只能确认到丢失报文段之前的序号。这会导致发送方需要重传丢失报文段以及其后的所有报文段，这被称为 Go-Back-N 协议的特点。

为了解决这个问题，TCP 引入了选择确认（Selective Acknowledgment, SACK）选项。当接收方收到乱序的报文段时，它可以在确认报文段的 SACK 选项中，精确地告知发送方它已经收到了哪些报文段，以及这些报文段的序号范围。发送方收到 SACK 选项后，就可以只重传那些丢失的报文段，而不是所有未确认的报文段，从而大大提高了传输效率。SACK 机制是 TCP 可靠传输机制的一个重要增强，尤其是在高丢包率的网络环境中，其优势更加明显。

## 4.5 流量控制与拥塞控制

### 4.5.1 流量控制：原理、机制与公式

流量控制（Flow Control）的目的是协调发送方和接收方的数据传输速率，防止发送方发送数据过快，导致接收方的缓冲区溢出。TCP 的流量控制机制是基于滑动窗口实现的。

接收方在每个 TCP 报文段的首部中，都有一个窗口（Window）字段，用来告诉发送方自己当前还可以接收多少字节的数据。这个窗口值，即接收窗口（rwnd），是接收方缓冲区中剩余空间的大小。

当发送方收到一个包含窗口值的确认报文段时，它会调整自己的发送窗口大小，确保发送的数据量不超过接收方的接收窗口大小。发送窗口的大小由两个因素共同决定：接收窗口（rwnd）和拥塞窗口（cwnd）。

发送方可发送的最大数据量，即发送窗口的大小，由以下公式决定：

$发送窗口大小 = \min(rwnd, cwnd)$

其中，rwnd 是接收方告知的窗口大小，cwnd 是拥塞控制算法决定的窗口大小。发送方必须确保自己已发送但尚未确认的数据量不超过这个发送窗口大小。

#### 流量控制的公式推导

假设发送方 A 发送了一个报文段，包含序号 Seq 和数据长度 L。

接收方 B 接收到该报文段后，其缓冲区已接收的字节数是 $S_{recv}$，可用缓冲区大小为 $Buffer_{free}$。

接收方 B 会发送一个确认报文段给 A，其中：

- 确认号 $Ack = S_{recv} + 1$
- 窗口大小 $Window = Buffer_{free}$

当发送方 A 收到这个确认报文段后，会更新其发送窗口。

- 发送窗口的左边界（$S_{left}$）更新为 $Ack$。
- 发送窗口的右边界（$S_{right}$）更新为 $Ack + Window$。

发送方 A 此时可以发送的数据范围是 $(S_{left}, S_{right}]$。

发送方 A 还需要考虑拥塞窗口 cwnd，因此实际可发送的数据量是 $\min(rwnd, cwnd)$。

#### 举例：

- 发送方 A 发送 1000 字节的数据，序号从 1000 开始。
- 接收方 B 的缓冲区大小为 5000 字节，已使用 0 字节。
- 接收方 B 收到数据后，发送确认报文段：$Ack=2000$，$Window=5000-1000=4000$。
- 发送方 A 收到确认后，将发送窗口左边界更新为 2000，右边界更新为 $2000 + 4000 = 6000$。发送方可以继续发送最多 4000 字节的数据。

如果接收方应用程序处理数据缓慢，导致缓冲区空间变小，它会将较小的窗口值发送给发送方，从而减慢发送方的发送速率，这就是流量控制的核心原理。

### 4.5.2 拥塞控制：基本思想与核心算法

拥塞控制（Congestion Control）的目的是防止过多的数据注入到网络中，导致网络中的路由器或链路因过载而性能下降，甚至崩溃。拥塞控制是一个全局性的问题，涉及到网络中的所有主机和路由器。TCP 采用了一套精妙的拥塞控制算法来动态调整发送速率，其核心思想是：“如果网络没有出现拥塞，就逐步提高发送速率；如果网络出现了拥塞，就立即降低发送速率。”

TCP 拥塞控制主要包括四个核心算法：慢启动（Slow Start）、拥塞避免（Congestion Avoidance）、快速重传（Fast Retransmit）和快速恢复（Fast Recovery）。

拥塞窗口（Congestion Window, cwnd）是拥塞控制的核心变量，它由发送方维护，是发送方在任何时刻可以发送的未确认数据量。发送窗口的大小由 $\min(rwnd, cwnd)$ 决定。

1. **慢启动（Slow Start）**

当 TCP 连接建立时，拥塞窗口 cwnd 初始化为一个较小的值，通常为 1 或 2 个报文段（MSS）。慢启动算法的特点是指数级增长。每收到一个新报文段的确认，拥塞窗口就增加一个 MSS。

流程：
- 初始：$cwnd = 1 \times MSS$
- 收到 1 个确认：$cwnd = 2 \times MSS$
- 收到 2 个确认：$cwnd = 4 \times MSS$
- 以此类推，拥塞窗口呈指数级增长。
- 慢启动阶段会一直持续到拥塞窗口达到一个慢启动门限（ssthresh）。

2. **拥塞避免（Congestion Avoidance）**

当拥塞窗口 cwnd 达到慢启动门限 ssthresh 时，TCP 进入拥塞避免阶段。拥塞避免阶段的增长方式是线性增长。每经过一个往返时间 RTT，拥塞窗口才增加一个 MSS。

流程：
- 拥塞窗口达到 ssthresh。
- 每收到一个确认，拥塞窗口增加 $\frac{1}{cwnd} \times MSS$。
- 每收到一个窗口大小的确认，拥塞窗口增加 1 个 MSS。
- 当网络出现拥塞时（超时或收到三个重复确认），就会触发拥塞处理机制。

3. **拥塞处理：超时与快速重传/恢复**

当网络出现拥塞时，TCP 会通过两种方式来检测：
- 定时器超时：当发送方重传定时器超时时，认为网络发生了严重拥塞。
- 收到三个重复的 ACK：当发送方连续收到三个对同一个报文段的确认（即重复确认），说明该报文段可能丢失，但网络中还有数据在流动。

**超时处理**：
- 慢启动门限 ssthresh 减半，新的值是当前拥塞窗口的一半，但最小为 2 个 MSS。
- 拥塞窗口 cwnd 重置为 1 个 MSS。
- 进入慢启动阶段，重新开始指数级增长。

**快速重传（Fast Retransmit）与快速恢复（Fast Recovery）**：
快速重传是当发送方连续收到三个重复确认时，立即重传丢失的报文段，而不必等待定时器超时。这表明网络中可能发生了丢包，但不是严重拥塞。

流程：
- 发送方收到三个重复 ACK。
- 立即执行快速重传，重传丢失的报文段。
- 执行快速恢复：
  - 慢启动门限 ssthresh 减半，新的值为当前拥塞窗口的一半。
  - 拥塞窗口 cwnd 设置为 $ssthresh + 3 \times MSS$（3 是因为收到了 3 个重复确认）。
  - 拥塞窗口以线性方式（拥塞避免）继续增长，每收到一个新确认，窗口增加 1 个 MSS。

快速重传和快速恢复机制可以在不等待超时的情况下，快速恢复网络传输，避免了回到慢启动阶段，从而提高了网络利用率。

## 4.6 端口与套接字：网络通信的标识与接口

### 4.6.1 端口号：应用进程的唯一标识

在多任务操作系统中，一台主机可以同时运行多个网络应用程序。端口号（Port Number）的引入，正是为了在运输层实现复用（Multiplexing）和分用（Demultiplexing），即在多个应用进程之间共享一个 IP 地址，并将接收到的数据报正确地交付给目标进程。

端口号是一个 16 位的正整数，范围从 0 到 65535。根据其使用方式，端口号被划分为三类：

- **熟知端口号（Well-Known Ports）**：0 到 1023。这些端口号通常由 IANA（互联网号码分配局）指定给一些常用的、标准的服务器应用。例如，HTTP 服务占用端口号 80，FTP 服务占用端口号 21，SMTP 服务占用端口号 25，DNS 服务占用端口号 53。这些端口号是固定的，客户端可以通过这些固定的端口号与服务器建立连接。
  
- **注册端口号（Registered Ports）**：1024 到 49151。这些端口号可以由 IANA 注册给特定的应用程序使用，以避免与熟知端口号冲突。虽然这些端口号不是标准协议的默认端口，但它们被广泛用于一些商业应用或非标准服务。
  
- **动态/私有端口号（Dynamic/Private Ports）**：49152 到 65535。这些端口号通常被称为临时端口号（Ephemeral Ports），在客户端发起连接时动态分配给客户端进程。客户端程序在发起连接时，通常会从这个范围中选择一个未被占用的端口号作为其源端口号。

端口号是运输层协议报文段首部中的一个重要字段，它与 IP 地址一起，构成了网络通信中的一个端点。

### 4.6.2 套接字：网络通信的编程接口

套接字（Socket）是网络编程中的一个抽象概念，它为应用程序提供了一个统一的接口，使得应用程序可以像操作本地文件一样进行网络通信。套接字可以看作是应用程序与运输层之间的“门面”，它将 IP 地址和端口号等底层网络信息封装起来，提供了一个更高级别的编程接口。

一个套接字由 IP 地址和端口号组成。

- **对于 TCP 协议**来说，一个 TCP 连接由一个唯一的四元组标识：
  $(源IP地址, 源端口号, 目的IP地址, 目的端口号)$
  
  这个四元组在连接建立后是固定的，可以唯一标识网络上的一个通信会话。
  
- **对于 UDP 协议**来说，一个 UDP 套接字由一个二元组标识：
  $(IP地址, 端口号)$
  
  因为 UDP 是无连接的，通信双方没有固定的会话概念，因此只需要标识一个通信端点即可。

在实际的网络编程中，程序员通过调用操作系统的套接字 API（Application Programming Interface）来创建、绑定、监听、连接、发送和接收数据。例如，使用 `socket()` 函数创建一个套接字，使用 `bind()` 函数将套接字与本地 IP 地址和端口号绑定，使用 `listen()` 函数监听来自客户端的连接请求，使用 `connect()` 函数向服务器发起连接，使用 `send()` 和 `recv()` 函数收发数据。

套接字这一抽象机制将复杂的底层网络协议细节（如报文段封装、序号、确认等）对上层应用透明化，使得应用程序开发者可以专注于业务逻辑的实现，而无需关心数据包是如何在网络中传输的。

## 4.7 运输层协议在实际中的应用

### 4.7.1 TCP 与 UDP 的选择：平衡可靠性与实时性

在实际应用开发中，选择使用 TCP 还是 UDP，通常是一个需要权衡可靠性与实时性的决策。

- **选择 TCP 的场景**：当应用对数据传输的可靠性和完整性有严格要求时，应优先选择 TCP。TCP 提供的可靠传输、流量控制和拥塞控制机制，能够确保数据不丢失、不重复、不乱序，并能够根据网络状况动态调整传输速率。典型的应用场景包括：
  - 文件传输（FTP）：确保文件内容完整无误地传输。
  - 网页浏览（HTTP/HTTPS）：网页的 HTML、CSS、图片等资源必须完整加载，否则会导致页面显示不正常。
  - 电子邮件（SMTP/POP3/IMAP）：确保邮件内容不丢失或损坏。
  - 远程登录（SSH）：确保命令和输出的准确无误。

- **选择 UDP 的场景**：当应用对实时性要求较高，而可以容忍少量数据丢失时，UDP 往往是更好的选择。UDP 协议的无连接、低开销特性，使得它能够以最快的速度传输数据，避免了 TCP 因重传和拥塞控制带来的额外延迟。典型的应用场景包括：
  - 实时音视频传输（VoIP、流媒体）：如网络电话、在线视频会议。即使有少量丢包，通过一些冗余编码或插帧技术，用户体验受到的影响很小，但如果为了重传而引入延迟，则会严重影响通信的流畅性。
  - 在线多人游戏：如第一人称射击游戏，玩家位置和状态需要实时更新。UDP 允许服务器快速广播信息，即使有少量数据丢失，客户端可以通过后续的数据更新来弥补，从而保证了游戏的低延迟。
  - 域名系统（DNS）：DNS 查询是一个简单的请求-响应模式，数据量小。使用 UDP 可以快速完成查询，如果查询失败，客户端可以快速重发，无需建立和释放连接的开销。
  - 物联网（IoT）：一些轻量级的传感器数据传输，如温度、湿度等，通常采用 UDP，因为数据量小，对实时性有一定要求，且设备资源有限，使用 TCP 的开销太大。

### 4.7.2 TCP 性能优化与未来发展

尽管 TCP 已经非常成熟和稳定，但随着网络带宽的不断提升和应用场景的多样化，人们也在不断地对 TCP 进行优化和改进。

- **拥塞控制算法的改进**：传统的 TCP 拥塞控制算法（如 Tahoe 和 Reno）在面对高延迟、高带宽网络（BDP，Bandwidth-Delay Product 很大的网络）时，性能表现不佳。为了解决这个问题，相继出现了许多新的拥塞控制算法，例如 CUBIC、BBR（Bottleneck Bandwidth and RTT）等。CUBIC 通过一个三次函数来增长拥塞窗口，以更激进的方式利用高带宽网络。BBR 则从根本上改变了拥塞控制的思路，它不再单纯依赖丢包作为拥塞信号，而是通过测量网络的瓶颈带宽和往返时间来确定发送速率，从而实现更高效、更公平的拥塞控制。

- **TCP 协议扩展**：为了应对新的需求，TCP 协议也增加了一些可选字段，例如 SACK（选择确认）用于提高重传效率，TSOPT（时间戳选项）用于精确地测量往返时间并防止序号回绕问题。

- **QUIC 协议**：QUIC（Quick UDP Internet Connections）是 Google 开发的一种基于 UDP 的传输层协议。它的目标是结合 TCP 的可靠性、流量控制等优点，同时解决 TCP 在连接建立延迟、队头阻塞（Head-of-Line Blocking）等方面的固有缺陷。QUIC 在应用层实现了可靠传输、加密、拥塞控制等功能，并且由于其基于 UDP，可以在一个连接中并行处理多个数据流，解决了 TCP 的队头阻塞问题。它正在被 IETF 标准化，有望成为未来互联网传输层协议的重要组成部分。

这些优化和发展都旨在让运输层协议更好地适应现代网络环境，为上层应用提供更高效、更稳定的数据传输服务。

## 4.8 总结与复习要点

本章我们全面、深入地学习了计算机网络中的核心组成部分——运输层。作为连接应用层和网络层的桥梁，运输层在实现端到端通信中扮演着至关重要的角色。

### 核心知识点回顾：

- **运输层概述**：理解运输层的功能是为应用进程提供端到端的逻辑通信，它通过端口号实现复用与分用。
- **UDP 协议**：掌握 UDP 无连接、尽力而为、低开销的特点，熟悉其 8 字节的首部格式及其字段含义，并能列举出其典型应用场景（如 DNS、VoIP、在线游戏）。
- **TCP 协议**：深入理解 TCP 的面向连接、可靠、全双工、面向字节流的特性。能够详细解释 TCP 报文段的 20 字节固定首部，尤其是序号、确认号、窗口、标志位等关键字段的作用。
- **TCP 连接管理**：掌握 TCP 连接建立的三次握手和连接释放的四次挥手的完整流程、状态转换以及各自的目的。
- **可靠传输机制**：理解 TCP 如何通过序号、确认应答、超时重传等机制来确保可靠传输，并掌握滑动窗口机制在提高传输效率中的作用。
- **流量控制**：理解流量控制的目的是协调发送方与接收方的速率，其核心机制是接收方通过 TCP 首部中的窗口字段来动态调整发送方的发送窗口大小。
- **拥塞控制**：掌握拥塞控制的全局性思想，并能详细描述四种核心算法：慢启动（指数增长）、拥塞避免（线性增长）、快速重传和快速恢复。理解拥塞窗口 cwnd 在拥塞控制中的核心作用。
- **端口与套接字**：理解端口号作为应用进程的唯一标识，并能区分熟知、注册和动态端口号。掌握套接字作为网络通信编程接口的概念，并能区分 TCP 和 UDP 套接字的组成。
