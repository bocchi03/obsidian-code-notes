
## 6.1 网络应用模型
计算机网络的核心价值在于其所承载的各种应用。这些应用通过不同的模型来组织和运行，其中最基础和常见的两种模型是客户-服务器模型（Client-Server Model, C/S）和对等模型（Peer-to-Peer Model, P2P）。理解这两种模型是深入学习应用层协议的基础。

### 客户-服务器模型（C/S 模型）

#### 定义与特点
客户-服务器模型是一种分布式应用架构，它将网络中的不同设备划分为两种角色：客户（Client）和服务器（Server）。在这个模型中，服务器是一个提供服务的强大、稳定、持续运行的实体。它通常拥有固定的IP地址和域名，用于处理来自多个客户端的请求，并管理资源，如网页、文件、数据库等。客户则是发起请求的一方，它们可以是个人电脑、手机、平板电脑等终端设备。客户端通常是按需启动，与服务器进行短暂的通信，获取所需服务后便可以断开连接。客户端不直接相互通信，所有的交互都必须通过服务器作为中介。

这种模型有几个显著特点：
- 角色分明：客户是服务请求方，服务器是服务提供方，职责清晰。
- 中心化：服务和数据集中存储在服务器上，方便管理和维护。
- 可扩展性：通过增加服务器数量（水平扩展）或提升服务器性能（垂直扩展），可以应对不断增长的客户请求。
- 易于管理：由于所有数据和逻辑都集中在服务器端，安全策略、数据备份和版本控制都相对容易实施。

#### 工作原理（请求-响应机制）
C/S 模型的核心是请求-响应（Request-Response）机制。其工作流程通常如下：
1. 服务器启动：服务器进程首先启动，并进入一个**监听（listening）**状态，等待客户端的连接请求。它会在一个预先定义好的端口上“守候”，这个端口号是服务类型的一个标识，比如Web服务的默认端口是80，FTP是21。
2. 客户端连接：客户端需要知道服务器的IP地址和端口号。当客户端需要某个服务时，它会向服务器发起一个连接请求，建立一条传输层的连接（通常是TCP连接）。
3. 客户端发送请求：连接建立后，客户端根据具体的应用层协议（如HTTP、FTP等）向服务器发送一个包含特定内容的请求报文。这个请求报文明确说明了客户端想要什么服务或资源。
4. 服务器处理请求：服务器接收到请求后，对其进行解析和处理。这可能涉及从硬盘读取文件、查询数据库、执行特定计算等。
5. 服务器发送响应：处理完成后，服务器生成一个响应报文，将处理结果或所需资源发送回客户端。
6. 客户端接收响应并关闭连接：客户端接收到响应后，解析报文并展示结果给用户。根据协议类型（如HTTP/1.1的持久连接），连接可能在一次请求-响应后立即关闭，也可能保持开放以供后续交互。

#### 优点与缺点
优点：
- 集中管理：服务器可以对所有用户和数据进行统一管理和控制，便于实施安全策略和数据备份。
- 高安全性：数据和业务逻辑集中在服务器端，可以更好地保护核心资产。
- 专业化分工：服务器端可以运行在高性能硬件上，处理复杂的计算和数据存储任务；客户端则可以专注于用户界面和交互，对硬件要求较低。
- 版本控制简单：软件升级和维护主要在服务器端进行，客户端只需更新少量代码甚至无需更新。

缺点：
- 单点故障：如果服务器发生故障，所有依赖该服务器的客户端都将无法使用服务。虽然可以通过负载均衡和冗余备份来缓解，但仍是潜在风险。
- 可扩展性挑战：当客户端数量激增时，服务器可能会成为性能瓶颈，需要复杂的扩展方案来应对。
- 高成本：服务器端需要高性能硬件和专业维护人员，初期投入和运维成本较高。
- 网络延迟：客户端与服务器的距离和网络状况会影响响应速度，尤其对于需要实时交互的应用。

#### 实例：Web 服务、FTP、Email
- **Web 服务（HTTP）**：我们每天浏览网页就是最典型的C/S模型。你的浏览器（客户端）向Web服务器（如Apache, Nginx）发送HTTP请求，服务器返回HTML、CSS、图片等资源。
- **文件传输协议（FTP）**：FTP客户端向FTP服务器请求上传或下载文件。服务器管理着文件目录和用户权限，客户端则通过命令行或图形界面与之交互。
- **电子邮件（SMTP/POP3/IMAP）**：你的邮件客户端（如Outlook, Gmail App）是客户端，而邮件服务器（如QQ邮箱服务器）是服务器。发送邮件时，客户端将邮件提交给SMTP服务器；接收邮件时，客户端从POP3或IMAP服务器拉取邮件。

### 对等（P2P）模型

#### 定义与特点
对等模型是一种去中心化的网络应用架构。在P2P模型中，网络中的所有设备（称为对等方，peer）都具有相同的地位，它们既可以作为服务请求方（客户端），也可以作为服务提供方（服务器）。每个对等方都可以直接与其他对等方进行通信和资源交换，而无需一个中心化的服务器作为中介。

P2P模型的特点与C/S模型形成鲜明对比：
- 去中心化：没有一个中心化的服务器，网络中的所有节点共同承担服务的提供和维护。
- 高可扩展性：网络的性能和容量随着新节点的加入而增加。更多的节点意味着更多的带宽和存储资源。
- 高健壮性：即使部分节点离线，整个网络仍然能够正常工作。没有单点故障问题。
- 自组织性：P2P网络通常能够自发地组织和维护自身，无需中央管理。

#### 工作原理（节点既是客户端也是服务器）
P2P模型的工作原理是“你为人人，人人为你”。一个节点在下载资源的同时，也在为其他节点提供上传服务。其核心思想是资源共享和负载均衡。

工作流程大致如下：
1. 加入网络：一个新节点首先需要找到网络中的其他节点，通常通过一个初始的“引导节点”（bootstrap node）或预设的节点列表来获得其他节点的地址。
2. 资源发现：新节点会向其他节点查询某个资源的可用性。这通常通过分布式哈希表（Distributed Hash Table, DHT）或其他索引机制实现，每个节点都存储一部分资源的索引信息。
3. 直接通信：一旦找到拥有所需资源的对等方，新节点会直接与该对等方建立连接，并请求下载资源。
4. 并发下载与上传：P2P的精髓在于“分块下载”。一个大文件会被分成许多小块，一个节点可以同时从多个拥有不同文件块的对等方下载，大大提高下载速度。同时，这个节点也会把自己已经下载好的文件块上传给其他需要的节点。

#### 优点与缺点
优点：
- 高可扩展性：随着用户数量增加，网络资源（带宽、存储）也随之增加，下载速度往往更快。
- 高健壮性与抗审查性：没有中心服务器，难以被单一实体控制或关闭。
- 低成本：无需维护昂贵的服务器集群，成本由所有参与者共同承担。

缺点：
- 安全性和信任问题：难以验证对等方身份和所提供资源的真实性。恶意节点可能提供病毒文件或虚假数据。
- 难以管理和维护：由于没有中央控制，难以实施统一的安全策略、版本更新或内容管理。
- 资源质量不稳定：资源的可用性取决于对等方是否在线。一个节点离线，它所持有的资源可能就不可用。
- 法律风险：由于其去中心化的特性，P2P网络常被用于非法内容（如盗版软件、电影）的传播，面临严格的法律监管。

#### 实例：BitTorrent、区块链
- **BitTorrent**：这是最著名的P2P文件共享协议。当你想下载一个大文件（如Linux发行版），你会下载一个“.torrent”文件，这个文件包含了 tracker 服务器地址和文件信息。你的BitTorrent客户端连接到 tracker 服务器获取拥有该文件其他对等方的列表，然后直接从这些对等方下载文件块，并同时将已下载的文件块上传给其他对等方。
- **区块链（Blockchain）**：比特币、以太坊等加密货币的底层技术就是P2P网络。每个参与者（节点）都保存着一份完整的账本（区块链），所有交易都是在节点之间直接广播和验证，没有中央银行或其他中心机构。

## 6.2 域名系统（DNS）
互联网上的设备通过IP地址（如192.168.1.1）进行通信。然而，IP地址是数字序列，对人类来说难以记忆。**域名系统（Domain Name System, DNS）**应运而生，它是一个庞大而复杂的分布式数据库，负责将人类可读的域名(如www.google.com) 转换为机器可识别的IP地址。可以说，DNS是互联网的“电话簿”。

### DNS 的作用与原理
#### DNS 的作用
DNS的核心作用是域名解析（Domain Name Resolution）。当你在浏览器中输入一个域名时，你的电脑并不知道这个域名对应的IP地址是什么。这时，它会向DNS系统发起查询，DNS系统会返回该域名对应的IP地址。随后，浏览器才能使用这个IP地址与目标服务器建立连接。

#### DNS 的原理
DNS系统是一个分层、分布式的数据库。它不是由一个单一的服务器来管理所有域名信息，而是由全球数以百万计的DNS服务器共同协作完成。这种分布式设计确保了DNS系统的高可用性、可扩展性和高效率。

### 域名层次结构
DNS域名采用**分层（hierarchical）**结构，形如host.sub.domain.tld.。从右向左，每一级都代表一个更广的范围。
- 根域（Root Domain）：位于域名层次结构的顶端，用一个空字符串表示（或一个点.）。全球有13组根服务器，它们存储了所有顶级域名的信息。
- 顶级域（Top-Level Domain, TLD）：由ICANN管理，分为：
  - 国家和地区顶级域（ccTLD）：如 .cn（中国）、.uk（英国）、.jp（日本）。
  - 通用顶级域（gTLD）：如 .com（商业组织）、.org（非盈利组织）、.edu（教育机构）、.gov（政府机构）。
  - 新的通用顶级域（new gTLD）：如 .app、.xyz、.online。
- 二级域（Second-Level Domain）：在顶级域下注册的域名，如google.com中的google。这是我们通常购买和使用的域名。
- 三级域（Third-Level Domain）：在二级域下创建的子域名，如mail.google.com中的mail。
- 主机名（Hostname）：通常是域名的最左部分，指定了该域名对应的具体主机，如www.google.com中的www。
  
总结：一个完整的域名是主机名.三级域.二级域.顶级域.，每一级之间用点分隔。

### 域名解析过程
当用户在浏览器中输入www.example.com 时，域名解析过程会非常复杂，但通常可以分为**递归查询（recursive query）和迭代查询（iterative query）**两种方式。
1. **本地DNS服务器（Local DNS Server）**：又称默认DNS服务器或DNS缓存服务器。通常由你的ISP（互联网服务提供商）提供，或由公司、学校自行设置。当你的计算机需要解析一个域名时，它首先向本地DNS服务器发起递归查询。
2. **根DNS服务器（Root DNS Server）**：如果本地DNS服务器没有缓存该域名信息，它会向根DNS服务器发起迭代查询，询问.com域名的权威DNS服务器地址。
3. **顶级域（TLD）DNS服务器**：根服务器返回.com顶级域名服务器的地址。本地DNS服务器再向.com TLD服务器发起迭代查询，询问example.com域名的权威DNS服务器地址。
4. **权威DNS服务器（Authoritative DNS Server）**：TLD服务器返回example.com的权威DNS服务器地址。该服务器是真正管理example.com域名的服务器，它知道所有关于example.com子域名的信息。本地DNS服务器最后向其发起迭代查询。
5. **返回结果**：权威DNS服务器返回www.example.com 对应的IP地址。
6. **本地DNS服务器缓存**：本地DNS服务器收到IP地址后，将其缓存起来，并返回给用户的计算机。
7. **用户计算机缓存**：用户的计算机也会将这个IP地址缓存起来，在TTL（Time-To-Live）有效期内，下次访问www.example.com 就不再需要查询DNS服务器。

### 递归与迭代
- **递归查询**：客户端（例如你的计算机）向本地DNS服务器发送查询请求，它要求本地DNS服务器必须给出最终的解析结果，而不是其他服务器的地址。
- **迭代查询**：DNS服务器（例如根服务器）在收到查询请求后，并不直接给出最终结果，而是告诉发起查询的服务器（例如本地DNS服务器）“你去问这个服务器”，并将另一个DNS服务器的地址返回。

小结：用户计算机到本地DNS服务器之间是递归查询，而本地DNS服务器到其他各级DNS服务器之间是迭代查询。

### DNS 服务器类型
- **根DNS服务器（Root Name Server）**：全球有13组，它们存储着所有TLD服务器的地址。
- **顶级域（TLD）DNS服务器**：负责管理所有特定TLD下的域名，如.com、.org等。
- **权威DNS服务器（Authoritative Name Server）**：负责特定域名的所有记录，如example.com的权威服务器知道www.example.com和mail.example.com的所有记录。
- **本地DNS服务器（Local DNS Server）**：也称为DNS缓存服务器，负责接收来自用户的查询请求，并缓存查询结果以提高效率。

### 资源记录类型（Resource Record, RR）
DNS数据库中的每条记录都是一个资源记录（RR），其通用格式是 (Name, Value, Type, TTL)。
- **A 记录（Address Record）**：将域名解析为IPv4地址。
  - Name：域名(如www.example.com)
  - Value：对应的IPv4地址（如93.184.216.34）
  - 考试口诀：“A记录是地址（Address）记录，记住是IPv4！”
- **AAAA 记录（IPv6 Address Record）**：将域名解析为IPv6地址。
  - Name：域名
  - Value：对应的IPv6地址
- **CNAME 记录（Canonical Name Record）**：别名记录，将一个域名解析到另一个域名。通常用于将www.example.com 解析到example.com ，或将负载均衡地址解析到真实地址。
  - Name：别名（如www.example.com）
  - Value：真实域名（如lb.example.com)
  - 注意：CNAME记录的Name不能同时拥有其他记录类型（如A记录）。
- **MX 记录（Mail Exchanger Record）**：邮件交换记录，指定接收该域名邮件的邮件服务器地址。
  - Name：域名（如example.com）
  - Value：邮件服务器的域名（如mail.example.com）
  - 特点：MX记录通常包含一个优先级字段，优先级数字越小表示优先级越高。
- **NS 记录（Name Server Record）**：域名服务器记录，指定一个域名由哪个DNS服务器来解析。
  - Name：域名（如example.com）
  - Value：负责解析该域名的权威DNS服务器的域名（如ns1.example.com）

### 缓存机制与 TTL
DNS的效率很大程度上依赖于缓存（Caching）。DNS查询结果会被本地DNS服务器和用户计算机缓存起来。
- **TTL（Time-To-Live）**：资源记录中的一个字段，表示该记录的缓存有效期。在TTL时间内，缓存的记录是有效的，下次查询会直接从缓存中返回，无需再次进行复杂的解析过程。当TTL过期后，缓存记录被清除，下次查询需要重新进行解析。
- **好处**：大大减少了DNS服务器的负载，缩短了域名解析时间。
- **风险**：如果域名对应的IP地址发生变化，在TTL过期前，用户仍然会访问旧的IP地址。因此，TTL值的设置是一个权衡，通常在几分钟到几小时之间。

### 常见 DNS 协议端口与报文格式
- **端口**：DNS协议默认使用UDP的53端口进行查询，因为UDP是无连接的，查询报文通常很小，使用UDP效率更高。但当DNS报文过大（如超过512字节）或进行区域传输（Zone Transfer）时，会使用TCP的53端口，以确保可靠性。
- **报文格式**：DNS报文分为**报头（Header）和问题/回答/授权/附加信息（Question/Answer/Authority/Additional）**四个部分。
  - **报头**：包含会话ID、标志位（如查询/响应、递归/迭代等）、问题计数、回答计数等关键信的信息。
  - **问题**：包含要查询的域名、查询类型（如A、MX等）和查询类别（通常是互联网）。
  - **回答**：包含查询结果的资源记录（RR），如果有多个，则有多个回答。
  - **授权**：包含负责该域名的权威DNS服务器的NS记录。
  - **附加信息**：通常包含授权服务器的IP地址，以便减少后续查询步骤。

### 考试易错点
DNS报文的四个部分非常重要，特别是报头中的各种标志位，常常是选择题和填空题的考点。

### DNS 安全（DNSSEC、防止域名劫持）
传统的DNS协议存在安全漏洞，最主要的是DNS缓存投毒和DNS欺骗。攻击者可以伪造DNS响应报文，将域名解析到恶意IP地址，从而劫持用户的流量。
- **DNSSEC（DNS Security Extensions）**：DNS安全扩展，通过使用**数字签名（Digital Signature）**来验证DNS响应的真实性和完整性。它在DNS记录中加入了公钥、签名等信息，客户端可以利用这些信息验证接收到的记录是否被篡改。DNSSEC的部署可以有效防止DNS缓存投毒等攻击，但其部署复杂且成本高。
- **域名劫持（DNS Hijacking）**：攻击者通过控制DNS服务器或篡改路由器设置，将用户的DNS请求重定向到恶意DNS服务器，从而返回错误的IP地址。
- **防止措施**：除了DNSSEC，还可以使用HTTPS-Only、**DoH（DNS over HTTPS）和DoT（DNS over TLS）**等新兴协议。
  - **DoH/DoT**：将DNS查询请求封装在加密的HTTPS/TLS会话中，防止ISP或中间人监听和篡改DNS查询。这使得DNS查询更加私密和安全。

## 6.3 文件传输协议（FTP）
**文件传输协议（File Transfer Protocol, FTP）**是一种用于在客户端和服务器之间传输文件的标准网络协议。FTP的历史非常悠久，是互联网早期最重要的应用之一。

### FTP 的工作原理（控制连接与数据连接）
FTP协议的一个独特之处在于它使用两个独立的TCP连接来完成文件传输任务。

- **控制连接（Control Connection）**：
  - **作用**：用于传输FTP命令和响应。它是一个持久的、长期的连接，贯穿整个FTP会话。
  - **端口**：客户端随机选择一个端口，向服务器的21端口发起连接。
  - **内容**：客户端通过这个连接发送用户名、密码、改变目录、列出文件列表等命令，服务器通过这个连接返回响应码和描述信息。

- **数据连接（Data Connection）**：
  - **作用**：专门用于传输文件本身。它是一个临时的连接，每传输一个文件就建立一次，传输完成后立即关闭。
  - **端口**：服务器的20端口或一个随机端口。

小结：控制连接是“指挥官”，负责发号施令；数据连接是“运输队”，专门负责搬运货物。这种设计使得FTP在命令交互和数据传输之间实现了分离。

### 主动模式与被动模式的区别
FTP的数据连接建立方式有两种，即主动模式（Active Mode）和被动模式（Passive Mode）。这两种模式的差异在于谁来发起数据连接。==(服务器视角)==

#### 主动模式（Active Mode）
- **控制连接建立**：客户端（Client）从随机端口向服务器（Server）的21端口发起连接。
- **客户端发送PORT命令**：客户端发送PORT A, B, C, D, E, F命令，告诉服务器它将使用自己的E * 256 + F端口（即E和F是端口号的高位和低位）来接收数据，并告知自己的IP地址A.B.C.D。
- **服务器发起数据连接**：服务器从20端口向客户端指定的E * 256 + F端口发起数据连接。

#### 优缺点分析（Active Mode）
- **优点**：对服务器端来说，实现简单，因为它总是从固定端口20向客户端发起连接。
- **缺点**：对客户端不友好。由于服务器主动向客户端发起连接，如果客户端位于防火墙或NAT（网络地址转换）设备之后，防火墙会阻止来自外部（服务器）的连接请求，导致数据连接无法建立。这使得主动模式在现代网络环境中越来越不实用。

#### 被动模式（Passive Mode）
- **控制连接建立**：同主动模式，客户端向服务器21端口发起连接。
- **客户端发送PASV命令**：客户端发送PASV命令，告诉服务器：“我处于被动状态，请告诉我你将使用哪个端口来传输数据，我会主动连接你。”
- **服务器发送响应**：服务器收到PASV命令后，随机开启一个端口（通常是1024以上的高端口），并返回227 Entering Passive Mode (A, B, C, D, E, F)响应，告诉客户端它的IP地址和数据端口号。
- **客户端发起数据连接**：客户端收到响应后，主动向服务器指定的端口发起数据连接。

#### 优缺点分析（Passive Mode）
- **优点**：对客户端友好。由于客户端主动发起所有连接，可以轻松穿越防火墙和NAT。这是目前FTP客户端默认的工作模式。
- **缺点**：对服务器来说，需要同时监听多个随机的高端口，增加了服务器管理的复杂性。

### 考试易错点
主动模式和被动模式的区别是FTP的必考点，务必理解是谁向谁发起数据连接。主动模式是服务器向客户端发起，被动模式是客户端向服务器发起。记忆口诀：“主动模式，服务器是主动的；被动模式，服务器是被动的。”

### FTP 命令与响应码
FTP的命令和响应都是明文的，便于理解和调试。

#### 常见命令（Commands）：
- **USER**：发送用户名。
- **PASS**：发送密码。
- **LIST**：列出当前目录下的文件和子目录。
- **CWD**：改变当前工作目录（Change Working Directory）。
- **RETR**：下载文件（Retrieve）。
- **STOR**：上传文件（Store）。
- **QUIT**：结束FTP会话。
- **PORT / PASV**：用于控制数据连接的模式。

#### 响应码（Reply Codes）：
- **2xx**：成功，命令成功完成。
- **3xx**：正在等待更多信息，如331 User name okay, need password.（用户名正确，需要密码）。
- **4xx**：临时错误，如421 Service not available, closing control connection.（服务不可用）。
- **5xx**：永久错误，如530 Not logged in.（未登录）。

### 优缺点与安全问题（明文传输）
优点：
- 高效：专门为文件传输设计，在网络环境良好时速度较快。
- 功能强大：支持目录管理、文件权限设置、断点续传等高级功能。

缺点与安全问题：
- **明文传输**：FTP在控制连接上以明文传输用户名、密码、命令等敏感信息。这使得攻击者可以很容易地通过抓包工具嗅探到这些信息，造成严重的安全风险。
- **防火墙问题**：主动模式下，防火墙配置复杂，导致连接失败。
- **设计陈旧**：FTP协议的设计已经跟不上现代网络安全和性能要求。

### 安全替代协议（SFTP、FTPS）
鉴于FTP的严重安全问题，出现了许多替代方案：
- **SFTP（SSH File Transfer Protocol）**：不是基于FTP协议的扩展，而是基于SSH协议的。它使用一个单一的连接，所有数据（包括命令和文件）都经过SSH加密，因此非常安全。
- **FTPS（FTP Secure）**：是FTP协议的TLS/SSL增强版。它在FTP的基础上引入了SSL/TLS加密层，可以加密控制连接或数据连接，或者两者都加密。FTPS需要专门的服务器和客户端支持。

总结：SFTP和FTPS都提供了安全的文件传输能力，但实现方式不同。SFTP是全新的协议，集成在SSH中；FTPS是对FTP的升级，在端口和工作流程上与FTP相似但加入了加密层。

## 6.4 电子邮件系统
电子邮件是互联网上最常用的应用之一。它的工作原理涉及多个组件和协议的协同工作。

### 电子邮件组成结构
一个完整的电子邮件系统由三个主要组成部分构成：
- **用户代理（User Agent）**：
  - **定义**：也就是我们日常使用的电子邮件客户端软件，如Microsoft Outlook、Thunderbird，或基于Web的邮件界面（Webmail），如Gmail、QQ邮箱网页版。
  - **作用**：为用户提供撰写、发送、接收、阅读、回复和转发邮件的接口。
  - **英文**：User Agent（UA）

- **邮件服务器（Mail Server）**：
  - **定义**：是电子邮件系统的核心，相当于邮件的“邮局”。每个邮件服务器都包含一个邮件队列（Mail Queue）和一个邮箱（Mailbox）。
  - **作用**：
    - 发送：当用户代理提交邮件后，邮件服务器会将邮件放入队列，并负责将其发送到收件人的邮件服务器。
    - 接收：当收到来自其他服务器的邮件时，它会将其存入收件人对应的邮箱中。
    - 存储：邮箱存储着用户收到的所有邮件，直到用户代理将它们读取走。
  - **英文**：Mail Server

- **协议（Protocols）**：
  - **定义**：用于在用户代理和邮件服务器之间、以及不同邮件服务器之间传输邮件的规则。
  - **主要协议**：
    - 发送协议：SMTP（Simple Mail Transfer Protocol）
    - 接收协议：POP3（Post Office Protocol version 3）和IMAP（Internet Message Access Protocol）

### 邮件传输协议（SMTP 工作机制）
SMTP是简单邮件传输协议，它用于发送邮件。无论是在用户代理将邮件提交给其本地的邮件服务器，还是在邮件服务器之间相互传输邮件，都使用SMTP协议。
- **端口**：SMTP默认使用TCP的25端口。
- **工作机制**：
  1. **连接建立**：发送方的邮件服务器（或用户代理）通过TCP向接收方的邮件服务器的25端口发起连接。
  2. **握手**：发送方发送HELO或EHLO命令，接收方返回响应。
  3. **发送者信息**：发送方发送MAIL FROM: <sender@example.com>命令，告诉接收方邮件的发送者是谁。
  4. **接收者信息**：发送方发送RCPT TO: <recipient@example.com>命令，告诉接收方邮件的收件人是谁。
  5. **发送数据**：发送方发送DATA命令，然后开始传输邮件的邮件头（Header）和邮件体（Body）。邮件体以一个单独的.符号结束。
  6. **关闭连接**：邮件传输完毕后，发送方发送QUIT命令，关闭TCP连接。

**特点**：SMTP是推（Push）协议，它将邮件从发送端“推”到接收端。它只负责邮件的传输，不负责邮件的存储或读取。此外，SMTP协议的命令和响应都是明文的。

### 邮件读取协议（POP3、IMAP）
POP3和IMAP是用于接收邮件的协议，它们负责将邮件从远程的邮件服务器“拉取”到用户的用户代理。

- **POP3（Post Office Protocol version 3）**
  - **工作机制**：当用户代理连接到邮件服务器时，它会下载所有未读邮件到本地计算机，然后从服务器上删除这些邮件。
  - **特点**：
    - **离线工作**：邮件下载到本地后，用户可以离线阅读。
    - **占用空间小**：服务器上不保存邮件，节省服务器存储空间。
    - **同步问题**：如果你在多台设备上使用POP3，邮件只会下载到其中一台设备上，其他设备将无法访问这些邮件，且邮件在服务器上被删除后无法恢复。
  - **端口**：默认使用TCP的110端口。

- **IMAP（Internet Message Access Protocol）**
  - **工作机制**：IMAP允许用户代理在不下载邮件的情况下直接在服务器上操作邮件，如创建文件夹、移动邮件、标记已读等。邮件默认保留在服务器上。
  - **特点**：
    - **多设备同步**：由于邮件始终保存在服务器上，无论你使用哪台设备，都能看到完全同步的邮件状态。
    - **在线工作**：需要持续的网络连接才能访问和操作邮件。
    - **服务器存储**：占用服务器存储空间较多。
  - **端口**：默认使用TCP的143端口。

### 对比
| 特点 | POP3 | IMAP |
| :--- | :--- | :--- |
| 邮件存储位置 | 下载到本地后从服务器删除 | 始终保存在服务器上 |
| 工作方式 | 离线工作 | 在线工作 |
| 多设备同步 | 差，容易导致邮件丢失 | 优，所有设备同步状态 |
| 服务器负载 | 低，邮件下载后即删除 | 高，需要持续存储邮件 |
| 适用场景 | 单设备、存储空间有限 | 多设备、追求同步、随时随地访问 |

### 邮件格式与 MIME 扩展
电子邮件的格式遵循RFC 822标准，它定义了邮件头和邮件体的结构。
- **邮件头（Header）**：包含From（发件人）、To（收件人）、Subject（主题）、Date（日期）等字段，每个字段都是字段名: 值的形式。
- **邮件体（Body）**：邮件的实际内容。

**MIME（Multipurpose Internet Mail Extensions）**：多用途互联网邮件扩展。RFC 822标准最初只支持纯文本（ASCII）邮件，无法发送图片、音频、视频、非ASCII字符（如中文）等。MIME扩展就是为了解决这个问题而诞生的。
- **MIME 的作用**：
  - 支持非ASCII字符集（如UTF-8）的邮件。
  - 支持多媒体附件，如图片、音频、视频等。
  - 支持多部分（Multipart）邮件，即将一封邮件分为多个部分（如纯文本部分和HTML部分），以兼容不同客户端。
  
- **MIME 关键头部字段**：
  - **MIME-Version: 1.0**：标识这是一封MIME邮件。
  - **Content-Type**：指定邮件内容的类型，如text/plain（纯文本）、text/html（HTML格式）、image/jpeg（JPEG图片）等。
  - **Content-Transfer-Encoding**：指定内容的编码方式，如base64。

### 邮件安全（SPF、DKIM、DMARC）
SMTP协议本身不具备身份验证和防伪造功能，这使得伪造发件人地址变得非常容易（邮件欺骗，Email Spoofing），这也是垃圾邮件和网络钓鱼攻击的根源。为了解决这一问题，出现了SPF、DKIM和DMARC等安全协议。
- **SPF（Sender Policy Framework）**：发件人策略框架。它是一个DNS记录，域名所有者通过在DNS中发布一个TXT记录，来声明哪些IP地址有权代表该域名发送邮件。接收方邮件服务器在接收邮件时，会查询发送者域名的SPF记录，以验证邮件是否来自合法的IP地址。
- **DKIM（DomainKeys Identified Mail）**：域名密钥识别邮件。它是一种数字签名技术。发件人邮件服务器在发送邮件时，会使用私钥对邮件进行数字签名，并将签名信息放在邮件头中。接收方邮件服务器通过查询发件人域名的DNS记录，获取公钥来验证签名的有效性。这可以确保邮件内容在传输过程中没有被篡改。
- **DMARC（Domain-based Message Authentication, Reporting, and Conformance）**：基于域名的邮件认证、报告和一致性。DMARC是SPF和DKIM的综合策略。域名所有者通过DMARC记录来告诉接收方服务器：“如果一封邮件同时未能通过SPF和DKIM验证，请执行什么操作？”（如拒绝、隔离、或只是报告）。DMARC还提供报告功能，让域名所有者了解其域名的邮件发送情况。

总结：
- **SPF**：验证发送者IP地址的合法性。
- **DKIM**：验证邮件内容在传输过程中未被篡改。
- **DMARC**：整合SPF和DKIM，并提供处理策略。

这三者共同构筑了现代邮件系统的反欺骗防线。

## 6.5 万维网与 HTTP 协议
万维网（World Wide Web, WWW）是互联网上最广泛使用的服务之一。它的核心是超文本和超媒体，以及用于传输这些资源的协议HTTP（HyperText Transfer Protocol）。

### HTTP 的发展（HTTP/0.9、1.0、1.1、2.0、3.0）
HTTP协议经历了多次演进，每一次更新都旨在解决旧版本的局限性，提升性能和安全性。
- **HTTP/0.9**：
  - **特点**：极其简单，只支持GET方法，用于请求HTML文件。服务器只返回HTML内容，没有头部信息。
  - **缺陷**：功能太少，不支持其他文件类型和交互。

- **HTTP/1.0**：
  - **特点**：引入了请求头（Request Header）和响应头（Response Header），可以传输更多元数据，如浏览器类型、文件类型等。支持POST、HEAD等更多方法。
  - **缺陷**：每个请求/响应都建立一个==非持久连接（Non-persistent Connection）==。即一次请求-响应后，TCP连接立即关闭。这导致每次获取网页上的图片、CSS、JS等资源时，都要重新建立TCP连接，产生大量延迟。

- **HTTP/1.1**：
  - **特点**：HTTP/1.1是目前互联网上应用最广泛的版本。
    - **持久连接（Persistent Connection）**：默认使用长连接。在一次请求-响应后，TCP连接不会立即关闭，可以复用该连接来传输后续请求，显著减少了连接建立的开销。
    - **管道化（Pipelining）**：允许客户端在发送第一个请求后，无需等待服务器响应，就可以连续发送多个请求。服务器按照顺序返回响应。
    - **缓存控制**：提供了更精细的缓存控制机制，如Cache-Control头部。
    - **Host头**：引入Host字段，允许一台服务器托管多个域名（虚拟主机），解决了IP地址的稀缺问题。
  - **缺陷**：
    - **队头阻塞（Head-of-Line Blocking）**：管道化虽然提高了效率，但如果服务器响应第一个请求很慢，后面的响应也都会被阻塞。
    - **明文传输**：HTTP/1.1协议本身是明文传输，不安全。

- **HTTP/2.0**：
  - **特点**：基于SPDY协议，旨在解决HTTP/1.1的性能瓶颈。
    - **二进制分帧**：将HTTP报文拆分成更小的二进制帧（Frame），所有帧在一个TCP连接上多路复用（Multiplexing）。
    - **多路复用**：允许一个TCP连接上同时并发传输多个请求和响应，彻底解决了HTTP/1.1的队头阻塞问题。
    - **头部压缩（Header Compression）**：使用HPACK算法压缩请求头，减少传输的数据量。
    - **服务器推送（Server Push）**：服务器可以在客户端请求HTML文件时，主动将页面所需的CSS、JS等资源推送到客户端，减少客户端的后续请求。
  - **注意**：HTTP/2.0通常要求使用HTTPS加密。

- **HTTP/3.0**：
  - **特点**：基于QUIC协议，是HTTP协议的又一次革命性升级。
  - **QUIC（Quick UDP Internet Connections）**：
    - **基于UDP**：放弃了TCP，直接在UDP上实现可靠传输、拥塞控制和加密，解决了TCP的队头阻塞问题。
    - **连接迁移**：客户端IP地址变化后（如从WiFi切换到蜂窝网络），连接可以无缝迁移，而无需重新建立。
    - **更快的TLS握手**：通过减少握手次数，实现更快的连接建立。
  - **优势**：彻底解决了底层TCP的队头阻塞，尤其在移动网络等弱网环境下表现更佳。

### HTTP 报文结构（请求行、头部、实体）
HTTP报文分为请求报文（Request Message）和响应报文（Response Message）。它们结构类似。

#### 请求报文
- **请求行（Request Line）**：方法 URL 协议版本
  - 示例：`GET /index.html HTTP/1.1`
- **请求头（Request Header）**：键: 值
  - 示例：
    - `Host: www.example.com`
    - `User-Agent: Mozilla/5.0`
    - `Accept-Language: zh-CN,zh`
    - `Connection: keep-alive`
- **空行**：一个空行，表示请求头结束。
- **请求体（Request Body）**：可选，通常用于POST、PUT等方法，包含提交的数据。

#### 响应报文
- **状态行（Status Line）**：协议版本 状态码 状态码描述
  - 示例：`HTTP/1.1 200 OK`
- **响应头（Response Header）**：键: 值
  - 示例：
    - `Content-Type: text/html; charset=utf-8`
    - `Content-Length: 1024`
    - `Server: Apache/2.4.18`
- **空行**：一个空行，表示响应头结束。
- **响应体（Response Body）**：包含服务器返回的实际内容，如HTML、图片、JSON数据等。

### 常见 HTTP 方法（GET、POST、PUT、DELETE 等）
HTTP定义了多种请求方法，用于指示对指定资源的不同操作。
- **GET**：**获取（Retrieve）**资源。
  - **特点**：幂等（Idempotent），多次执行结果相同。安全（Safe），只读操作，不会改变服务器状态。
  - **数据**：数据以URL参数的形式传输。
  
- **POST**：**提交（Submit）**数据，用于向服务器提交实体（如表单数据、文件）。
  - **特点**：不幂等，每次提交都可能创建新资源。不安全，会改变服务器状态。
  - **数据**：数据放在请求体中传输。

- **PUT**：**更新（Update）**资源。用于将请求体中的数据完整替换掉URL指定的资源。
  - **特点**：幂等。

- **DELETE**：**删除（Delete）**资源。用于删除URL指定的资源。
  - **特点**：幂等。

- **HEAD**：类似于GET，但服务器只返回响应头，不返回响应体。常用于检查资源是否存在或获取其元数据。
- **OPTIONS**：用于查询服务器支持的HTTP方法。
- **TRACE**：用于回显服务器收到的请求，常用于调试。

### 考试易错点
GET和POST的区别是面试和考试的重点。
- **GET**：获取资源，参数在URL中，不安全，幂等。
- **POST**：提交数据，参数在请求体中，不幂等，不安全。

### 状态码分类与示例
HTTP状态码是服务器对请求的处理结果的反馈。
- **1xx**：信息（Informational），表示请求已被接收，继续处理。
  - 示例：`100 Continue`：表示客户端应该继续发送请求体。
  
- **2xx**：成功（Successful），表示请求已被成功接收、理解、并接受。
  - 示例：
    - `200 OK`：请求成功，最常见的状态码。
    - `201 Created`：请求成功，并创建了新资源。
    - `204 No Content`：请求成功，但没有返回响应体。

- **3xx**：重定向（Redirection），需要进一步操作以完成请求。
  - 示例：
    - `301 Moved Permanently`：永久重定向。
    - `302 Found`：临时重定向。
    - `304 Not Modified`：客户端本地缓存的版本未修改，可以使用缓存。

- **4xx**：客户端错误（Client Error），请求有语法错误或无法被服务器执行。
  - 示例：
    - `400 Bad Request`：请求报文有语法错误。
    - `401 Unauthorized`：请求需要用户认证。
    - `403 Forbidden`：服务器理解请求，但拒绝执行。
    - `404 Not Found`：服务器找不到请求的资源。

- **5xx**：服务器错误（Server Error），服务器在处理有效请求时失败。
  - 示例：
    - `500 Internal Server Error`：服务器内部错误。
    - `503 Service Unavailable`：服务器暂时无法处理请求，通常是过载或维护。

### Cookie 与 Session 管理机制
HTTP协议是无状态（Stateless）的，即服务器不会记住每个客户端的状态。这对于简单请求没有问题，但对于需要用户登录等状态的应用则是个大问题。Cookie和Session就是用来解决这个问题的。

- **Cookie**：
  - **定义**：是服务器发送给浏览器的一小段文本信息，浏览器将其存储在本地，并在下次访问同一服务器时将其发送回去。
  - **工作机制**：
    1. 用户第一次访问服务器，服务器响应报文中包含一个Set-Cookie头部，设置一个Cookie。
    2. 浏览器接收到Cookie后，将其存储起来。
    3. 下次浏览器向同一服务器发送请求时，会自动在请求头中带上Cookie字段。
  - **特点**：
    - ==存储在客户端（浏览器）。==
    - 可以设置过期时间。
    - 大小限制（通常4KB）。
    - 可以被浏览器禁用，存在安全风险（如被XSS攻击）。

- **Session**：
  - **定义**：是服务器端用来保存用户状态的机制。
  - **工作机制**：
    1. 用户第一次登录时，服务器创建一个Session对象，并为该Session生成一个唯一的Session ID。
    2. 服务器将Session ID通过Set-Cookie头部发送给浏览器。
    3. 浏览器将Session ID保存在Cookie中。
    4. 后续请求中，浏览器都会带着Session ID的Cookie，服务器通过这个ID找到对应的Session对象，从而识别用户。
  - **特点**：
    - 存储在服务器端。
    - 安全，用户无法直接修改Session中的数据。
    - Session ID通过Cookie传递，如果禁用Cookie，可以通过URL重写等方式传递Session ID。

### 总结
Cookie主要在客户端保存状态，而Session在服务器端保存状态，Session ID是连接两者关系的桥梁。

### HTTPS（SSL/TLS 握手过程与安全性）
HTTP是明文传输，存在被窃听、篡改和伪造的风险。HTTPS（HyperText Transfer Protocol Secure）就是在HTTP的基础上加入了SSL/TLS协议，实现了加密传输和身份认证，确保通信的安全性。
- **SSL/TLS（Secure Sockets Layer / Transport Layer Security）**：
  - **作用**：在应用层和传输层之间提供一个加密层，确保数据传输的机密性、完整性和认证性。
  - **端口**：HTTPS默认使用TCP的443端口。

### TLS 握手过程（非常重要！）
1. **客户端打招呼（Client Hello）**：客户端向服务器发送一个Client Hello报文，包含支持的TLS版本、加密套件列表、随机数等。
2. **服务器回应（Server Hello）**：服务器选择一个加密套件，并返回Server Hello报文，包含选择的加密套件、服务器的随机数，以及服务器的数字证书（Certificate）。
3. **客户端验证证书**：客户端收到证书后，验证其有效性：
   - 证书是否由可信的**CA（Certificate Authority）**颁发？
   - 证书是否过期？
   - 证书中的域名是否与访问的域名一致？
   - 如果验证失败，浏览器会弹出警告。
4. **客户端生成预主密钥**：验证通过后，客户端生成一个预主密钥（Pre-Master Secret），并使用证书中的公钥对其进行加密。
5. **客户端发送加密密钥**：客户端将加密后的预主密钥发送给服务器。
6. **服务器解密**：服务器使用自己的私钥解密预主密钥。
7. **生成会话密钥**：客户端和服务器现在都拥有客户端随机数、服务器随机数和预主密钥，可以共同计算出对称会话密钥（Session Key）。
8. **加密通信**：握手结束。后续所有的数据传输都将使用这个对称会话密钥进行加密和解密。

总结：TLS握手过程实现了非对称加密（公钥/私钥）在建立连接时安全地交换对称会话密钥，然后使用高效的对称加密进行后续通信。这兼顾了安全性和性能。

## 6.6 网络应用安全
应用层的安全漏洞是网络攻击的常见入口。了解这些攻击方式并掌握防御手段至关重要。

### 应用层常见攻击方式
- **XSS（Cross-Site Scripting）跨站脚本攻击**
  - **原理**：攻击者在网页中注入恶意脚本，当用户访问该网页时，恶意脚本会在用户的浏览器中执行，窃取用户的Cookie、Session信息，或进行其他恶意操作。
  - **防御**：对用户输入进行严格的过滤和转义，尤其是<、>、'、"等特殊字符。设置HttpOnly属性的Cookie，防止JavaScript脚本读取。

- **SQL注入（SQL Injection）**
  - **原理**：攻击者在Web应用的输入框中，输入恶意的SQL代码片段，利用程序未对输入进行有效过滤的漏洞，来欺骗数据库执行恶意命令，如窃取、修改或删除数据。
  - **防御**：
    - **使用参数化查询（Parameterized Query）**或预处理语句（Prepared Statement），将SQL语句和数据分开处理。
    - 对用户输入进行严格的输入验证和过滤。
    - 对数据库用户权限进行最小化原则设置。

- **钓鱼攻击（Phishing）**
  - **原理**：攻击者伪装成知名服务商（如银行、社交网站），通过邮件、短信等方式诱骗用户访问伪造的网站，输入个人敏感信息（用户名、密码、信用卡号等）。
  - **防御**：
    - 用户应养成仔细核对网站URL、检查证书信息的习惯。
    - 启用多因素认证（MFA）。
    - 邮件服务器部署SPF、DKIM、DMARC等反欺骗协议。

- **中间人攻击（Man-in-the-Middle Attack, MITM）**
  - **原理**：攻击者截取客户端和服务器之间的通信，伪装成双方，窃听或篡改通信内容。
  - **防御**：使用HTTPS。TLS/SSL握手过程中，客户端会验证服务器的数字证书，确保通信对象的身份，并建立加密通道，防止被窃听和篡改。

- **DDoS（Distributed Denial of Service）分布式拒绝服务攻击**
  - **原理**：攻击者利用大量被控制的计算机（僵尸网络），同时向一个目标服务器发送海量请求，耗尽服务器的带宽、CPU或内存资源，使其无法正常提供服务。
  - **防御**：
    - 使用**CDN（内容分发网络）**分散流量。
    - 部署**WAF（Web Application Firewall）**或专业的DDoS清洗服务。
    - 进行流量分析和异常检测。

### 加密与认证机制
- **加密（Encryption）**：
  - **对称加密（Symmetric Encryption）**：加密和解密使用同一个密钥。速度快，效率高。缺点是密钥分发困难且不安全。
    - **算法**：AES、DES。
  - **非对称加密（Asymmetric Encryption）**：加密和解密使用一对密钥：公钥（Public Key）和私钥（Private Key）。公钥加密的数据只能用对应的私钥解密。安全性高，但计算量大，速度慢。
    - **算法**：RSA。

- **认证（Authentication）**：
  - **数字证书（Digital Certificate）**：用于验证服务器身份。证书包含公钥、域名、颁发者信息等，由权威CA签发。
  - **数字签名（Digital Signature）**：用于验证数据的完整性和来源。发送方使用私钥对数据摘要进行签名，接收方使用公钥验证。

### 安全传输协议
- **HTTPS**：在HTTP的基础上加入了TLS/SSL协议，提供加密和身份认证。
- **SSH（Secure Shell）**：用于远程登录和执行命令。它替代了明文传输的Telnet，提供了强大的加密和认证机制，确保远程会话的安全。
- **S/MIME（Secure/Multipurpose Internet Mail Extensions）**：用于对电子邮件进行加密和数字签名，确保邮件内容的机密性、完整性和发件人的身份认证。

## 6.7 P2P 应用与流媒体
除了文件共享，P2P模型还在流媒体和CDN等领域扮演着重要角色。

### P2P 文件共享原理（BitTorrent 协议）
BitTorrent协议是P2P文件共享的典型代表，其工作原理如下：
- **种子文件（.torrent）**：用户首先需要下载一个.torrent文件。这个文件很小，包含文件的元数据（文件名、大小、分块大小）以及一个或多个Tracker服务器的地址。
- **Tracker服务器**：Tracker服务器不存储文件内容，它的作用是协调和索引。当一个用户（Peer）启动下载时，它会连接Tracker服务器，告知自己正在下载哪个文件。Tracker服务器会返回一个拥有该文件的其他Peer列表。
- **对等方（Peer）**：通过Tracker服务器获得Peer列表后，你的BitTorrent客户端会直接与其他Peer建立连接。
- **分块下载**：BitTorrent将文件分割成许多固定大小的文件块（chunks）。客户端会同时从多个拥有不同文件块的Peer下载。
- **边下载边上传**：BitTorrent的核心思想是**“奖励”上传者**。它有一个**“Choking”算法**，优先将自己的文件块上传给那些给自己上传得多的Peer。这鼓励了每个参与者都为网络做出贡献。
- **分布式哈希表（DHT）**：现代BitTorrent客户端通常使用DHT来替代或补充Tracker服务器。DHT是一个去中心化的分布式索引系统，每个
节点都存储一部分索引信息，无需依赖中心化的Tracker服务器。这使得BitTorrent网络更加健壮和去中心化。

### 流媒体传输协议（RTSP、HLS、DASH）
流媒体是指将视频、音频等连续媒体数据，通过网络实时传输并播放。
- **RTSP（Real-Time Streaming Protocol）**：实时流协议。RTSP是一个控制协议，用于客户端向流媒体服务器发送命令，如播放（PLAY）、暂停（PAUSE）、快进、快退等，类似于一个远程控制。它本身不传输数据，而是通过RTP/RTCP协议来传输实际的媒体数据。
- **RTP（Real-time Transport Protocol）**：实时传输协议。RTP协议在UDP上运行，负责对媒体数据进行打包和传输。它会给每个媒体包加上时间戳（Timestamp）和序列号（Sequence Number），以便接收端能够进行抖动缓冲（Jitter Buffer）和顺序重排，提供流媒体的实时性。
- **HLS（HTTP Live Streaming）**：苹果公司开发的流媒体协议。
  - **原理**：HLS将视频流切成很小的**.ts文件（MPEG-2 Transport Stream），并通过一个.m3u8的索引文件**来描述这些.ts文件。客户端只需下载这个.m3u8文件，就能按顺序下载并播放.ts文件。
  - **特点**：基于HTTP协议，可以方便地利用Web服务器和CDN进行分发，穿透防火墙能力强。支持自适应比特率（Adaptive Bitrate），可以根据网络状况自动切换到高/低画质的视频流，提供流畅的观看体验。
- **DASH（Dynamic Adaptive Streaming over HTTP）**：国际标准的HTTP流媒体协议。
  - **原理**：与HLS类似，将视频切片，通过**.mpd的描述文件**来组织和索引。
  - **特点**：是一个开放标准，与HLS相比，兼容性更好。同样支持自适应比特率。

### 总结
早期的流媒体使用RTSP/RTP，但其穿透防火墙能力弱。现代流媒体则普遍采用基于HTTP的HLS和DASH协议，利用了HTTP的优势，并结合了CDN技术，实现了高效、稳定的流媒体分发。

## 6.8 本章小结与复习思考题
### 关键概念总结
- **网络应用模型**：C/S（中心化，请求-响应）、P2P（去中心化，对等方）。
- **DNS**：域名解析系统，分层分布式数据库，将域名解析为IP地址。理解递归查询与迭代查询。
- **FTP**：文件传输协议，使用控制连接（21）和数据连接，分主动模式和被动模式。
- **电子邮件**：三大部分（用户代理、邮件服务器、协议），三大协议（SMTP发送，POP3/IMAP接收），MIME扩展多媒体。
- **万维网与HTTP**：HTTP协议是万维网的核心，从HTTP/1.0的非持久连接到HTTP/1.1的持久连接，再到HTTP/2.0的多路复用和HTTP/3.0的QUIC，不断演进。
- **HTTPS**：HTTP + SSL/TLS，通过数字证书和加密技术保障通信安全。
- **应用安全**：XSS、SQL注入、钓鱼、DDoS是常见攻击，HTTPS、CDN、WAF是重要防御手段。
- **流媒体**：RTSP（控制）、RTP（传输）、HLS/DASH（基于HTTP的自适应流媒体）。
- **CDN**：内容分发网络，通过缓存和就近分发技术加速内容传输。

### 重要公式与协议结构复盘
- **FTP数据端口计算**：在主动模式PORT A, B, C, D, E, F中，数据端口为E * 256 + F。
- **DNS报文结构**：报头、问题、回答、授权、附加信息。
- **HTTP报文结构**：请求行/状态行、头部、空行、实体。

### 常见考试题与易错点分析
- **C/S与P2P模型的优缺点对比**：这是最基础的知识点，需要深入理解。考试常考场景题，如“某公司要搭建一个数据中心，应该选择哪种模型？”
- **DNS的解析过程**：递归查询和迭代查询的区别是必考点。务必画图理解，分清用户计算机与本地DNS是递归，本地DNS与各级DNS是迭代。
- **FTP的主动模式与被动模式**：理解其核心区别在于谁发起数据连接，以及这两种模式在防火墙下的表现。
- **邮件协议的区分**：SMTP只用于发送，POP3/IMAP只用于接收。POP3和IMAP的区别在于邮件是否保留在服务器上。
- **HTTP的版本演进**：理解HTTP/1.0、1.1、2.0、3.0各自解决了什么问题，尤其是持久连接、队头阻塞和多路复用。
- **HTTP状态码**：掌握200、301、302、304、400、403、404、500、503等常见状态码的含义。
- **HTTPS的TLS握手过程**：这是本章最复杂也最核心的知识点之一，务必理解对称加密与非对称加密的结合使用。

### 复习口诀
- **DNS**：“递归问本地，迭代找权威，TTL缓存不能忘，安全防投毒。”
- **FTP**：“控制21，数据20，主动服务器连，被动客户端连。”
- **邮件**：“SMTP推邮件，POP3拉走删，IMAP在线同步全。”
- **HTTP**：“1.0短连接，1.1长连接，2.0多路复用，3.0跑QUIC。”
- **HTTPS**：“公钥加密会话密钥，私钥解密会话密钥，最后对称传数据。”
